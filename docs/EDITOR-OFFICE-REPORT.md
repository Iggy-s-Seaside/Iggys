# Specials Editor — Office Report (2026-07-11)

_Owner directive: "full office session understanding the editor — even from scratch or with Rust, I want it to work, and work well." 41-agent office: 5 domain mappers → 5 seeded defect hunters → adversarial verification of every finding → principal-engineer architecture judge. 29 findings confirmed (1 rejected); 2 stale entries about the already-landed pan-clamp fix (611f655) dropped from this ledger._

## The owner-reported bug (fixed first, by hand)

**Canvas jumped to the bottom corner on any workspace click.** Root cause: `useCanvasGestures.handlePointerUp`'s pan clamp used a single formula whose bounds INVERT (min > max) whenever the canvas fits inside the viewport — the normal fit-to-view state — so `Math.max(min, Math.min(pan, max))` slammed the pan to `viewport − 0.75·scaled` (bottom-right corner) on every background click. Fixed in `611f655`: two-regime `clampPanAxis` (exported + regression-tested), plain clicks (≲3px travel) never clamp, and a gray-workspace click now deselects instead of being swallowed.

## Architecture verdict (judge, verbatim)

## Verdict: Harden. Do not rewrite. Not Konva/Fabric, not Rust/WASM.

### (a) The architecture is sound; the defect list is a small number of design gaps wearing a long tail of symptoms

I read the reducer, the two gesture hooks, the interaction hook, the export pipeline, and the surface inventory the office built, plus confirmed current git state (`git log` shows the pan-clamp fix already landed as commit `611f655`, working tree clean — that finding is stale, not a blocker).

Sorting the 24 tracked defects by root cause, not by symptom, they collapse into **four design gaps**, not twenty-four independent failures:

| Root cause | Defects it explains |
|---|---|
| **No single gesture arbiter** — three independent pointer systems (`useCanvasGestures` viewport pan, `useElementInteraction` element drag/resize/rotate, `DomCanvas`'s bare `handleBackgroundPointerDown`) reconciled only by scattered `stopPropagation()` calls, no pointerId keying | pan-clamp corner jump, mobile pinch/pan no clamp, desktop pan stuck-on with no pointer capture, shared un-keyed `dragRef` corrupting multi-touch, 40ms tap-promotes-to-drag noise, resize-anchor drift, Y-snap computed-but-never-applied |
| **No overlay arbiter** — 10+ independently-booleaned surfaces (`mobileFontPickerOpen`, `mobileBlendPickerOpen`, `libraryOpen`, `mobileFiltersOpen`, `mobileSheet`, `templatePickerOpen`…) each hand-wired to Escape/backdrop/z-index by convention (`closeAllOverlays()`), not by a shared owner | Escape-deselects-layer-as-a-side-effect, MobileFontPicker/BlendPicker ghost-reopen, ImageLibrary rendering under MobileToolbar's z-index, Add-menu backdrop trapped by toolbar's transform, MobileFilterBar unreachable, duplicate desktop/mobile template pickers |
| **Dual, hand-maintained render pipelines** — DOM+CSS is the live preview (`TextElement`/`ImageElement`/`VideoElement`), `exportToCanvas.ts` is a *second*, independently-written canvas-2D renderer that must manually replicate every CSS property | idb:// images vanishing on export, templates that never recover, blend-mode+overlay compositing order wrong, underline export diverging on wrap/letter-spacing, GIF short-loop freeze |
| **Ad hoc transient/history contract** — `pendingPast` poked directly from three call sites instead of through a `begin/commit/cancel` API | UNDO/REDO discarding an in-flight drag baseline, MAX_HISTORY off-by-one |

That's the signature of **a reasonably-factored app with under-defended seams**, not an unsound one. The hooks are already split by concern (`useEditorState`, `useElementInteraction`, `useCanvasGestures`, `useDraftPersistence`) — the 1800-line `SpecialEditor.tsx` is mostly wiring/JSX for a genuinely large surface (toolbar, panels, six overlay types, keyboard shortcuts), not a god-object doing everyone's job.

**Why a canvas-library or Rust rewrite doesn't buy what it looks like it buys:**
- Konva/Fabric would relocate the gesture-arbitration bug class, not eliminate it — you'd still hand-write pan/pinch/resize/snap math, just against a Stage/Layer API instead of raw DOM pointer events. Same bug surface, new syntax.
- It genuinely *would* kill the dual-render-pipeline category, since Konva's preview and export share one scene graph — that's the one legitimate architectural argument for it. But that's 5 of 24 defects, and cheaper to fix directly (see refactor #3 below) than to buy by rewriting the other ~19 bugs' worth of surrounding code from scratch, with full regression risk, on a **live production app a family bar runs nightly**.
- Rust/WASM solves CPU-bound problems (heavy filter compute, huge-canvas encoding). Nothing in this defect list is a performance problem — poster-sized stills and short GIFs, not video timelines. The owner's frustration is *correctness*, not *speed*.
- Rewrites don't fix logic bugs — they just give you one shot at not reintroducing them, while guaranteeing you introduce new ones. Every defect here already has a precise, one-function root cause identified by the office's own mapping. That's the textbook signature for "harden," not "rebuild."

**Cost comparison:** harden is ~1–2 weeks of surgical, independently-shippable fixes with the existing `test-editor`/`ux-gauntlet` skills verifying each one against the live build, zero downtime, zero regression blast radius outside the touched function. A Konva/Fabric migration is a from-scratch rebuild of every element renderer, the entire interaction/gesture layer, the export pipeline, and the template/layer JSON schema — 4–8 weeks minimum — during which the owner's top-priority bug and everything else stays exactly as broken as it is today, for a payoff (export fidelity) obtainable directly for a fraction of the cost.

### (b) The five refactors, ranked by payoff

1. **Single gesture arbiter.** One pointerId-keyed state machine owning "what does this pointerdown mean" (target + modifiers + current mode), replacing the three independently-reconciled systems (`useCanvasGestures`, `useElementInteraction`'s `dragRef`, `DomCanvas`'s bare background handler) and their `stopPropagation()`-based truce. This single change forecloses seven of the highest-severity findings at once: the pan-clamp class, desktop-pan-stuck-on, multi-touch corruption via the shared un-keyed `dragRef`, and the tap-vs-drag noise.
2. **Overlay arbiter.** Replace 10+ independent booleans with one `activeOverlay: OverlayId | null` (discriminated union) driving a generic `<OverlayHost>` that centralizes focus-trap, Escape, backdrop, z-index, and portal target in one place. Kills the Escape-deselect bleed, the FontPicker/BlendPicker ghost-reopen, the ImageLibrary z-index-under-toolbar bug, and the unreachable MobileFilterBar entry point structurally, instead of four separate patches that can drift again.
3. **Shared "layer paint spec."** Extract each layer type's visual computation (text wrap/underline/letter-spacing, blend+overlay composite order, gradient stop parsing) into pure functions consumed by *both* the DOM/CSS builders and `exportToCanvas.ts`. This is the cheap 80% substitute for a canvas-library rewrite — it makes the two renderers structurally unable to diverge again, fixing the underline, blend/overlay, and gradient-fidelity bugs at the root.
4. **Explicit transient-commit contract on the history reducer.** Replace ad hoc `pendingPast` pokes with `beginTransient()/commitTransient()/cancelTransient()`, and route UNDO/REDO through `cancelTransient()` instead of nulling the field directly. Fixes the drag-baseline-discard bug and, in the same edit, the `MAX_HISTORY` off-by-one.
5. **Single media-resolution boundary.** One `resolveMediaSrc(layer)` used by every consumer (DOM `<img>`/`<video>` *and* `exportToCanvas`'s `preloadImage`), instead of `VideoElement.tsx` quietly resolving `idb://` itself while the export path never does. Directly fixes both critical media bugs (vanishing images, unrecoverable templates) and forecloses the next layer type forgetting to resolve `idb://`.

Do these five in order 1→5; each is independently shippable and verifiable, and together they retire essentially the entire high/critical list without touching unrelated code.

### (c) If a rewrite is ever warranted — the trigger and the path

Not now. It becomes the right call only if the product grows into something the DOM-canvas model genuinely can't do: real-time multi-user collaboration on one poster, WebGL-grade image filters/vector shapes at scale, or the paint-spec consolidation (refactor #3) still leaving export drift after a real attempt. If that day comes:

- **Strangler-fig, not big-bang.** Keep `EditorState`/reducer and the layer JSON schema (already renderer-agnostic) as the contract. Swap the render layer only: introduce a Konva `Stage`/`Layer` renderer behind the existing `DomCanvas` interface, land it for one layer type (start with `image`, the highest-fidelity-risk type) behind a feature flag, verify pixel parity against the current export, then migrate `text`/`divider`/`video` one at a time.
- **Export becomes trivial** once preview *is* the canvas tree (`stage.toDataURL()`), so `exportToCanvas.ts`/`exportToGif.ts` shrink to almost nothing — that's the real payoff, realized only once every layer type has migrated, not before.
- **Gesture code still gets rewritten by hand** against Konva's event model — budget for refactor #1's design even in this path, since Konva doesn't give you pan-clamp/snap/multi-touch for free.
- **Never touch Rust/WASM** for this surface — there's no compute bottleneck here to justify it; it would add a build-toolchain and debugging-surface cost with no corresponding defect it fixes.
